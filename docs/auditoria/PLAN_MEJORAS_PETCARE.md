# Plan de mejoras de PetCare

Este plan es una propuesta nacida de la auditoría. No se implementó ningún cambio funcional. La matriz de autorización y requisitos está en [matriz](MATRIZ_CUMPLIMIENTO_REQUISITOS.md); los informes especializados enlazan los archivos de evidencia.

| Etapa | Objetivo y alcance | Archivos/áreas candidatas | Dependencias y riesgos | Pruebas / aceptación |
|---|---|---|---|---|
| 1. Seguridad y autenticación | Diseñar segundo factor separado de email; validar refresh/logout y política rate-limit multi-instancia; comprobar OAuth con cuentas controladas y configuraciones externas. | `backend/src/services/{auth,oauth,session,verification}.service.ts`, middleware auth/rate-limit; `mobile/src/contexts/AuthContext.tsx`, README. | Aprobación de política y método MFA; secretos OAuth/SMTP no pasar a mobile; compatibilidad con usuarios existentes. | Pruebas unitarias/DB solo en `_test`; MFA enrolar/desafiar/recuperar; logout/reuse refresh; E2E por proveedor en staging. |
| 2. Roles y permisos | Exportar grants efectivos anonimizados; revisar cada endpoint y alcance; documentar roles canónicos vs extensibilidad; pruebas negativas. | `backend/src/routes/*`, permission middleware, repositories authorization/clinic/admin; admin screens/services. | Snapshot de grants autorizado, migraciones fuente restauradas; riesgo de lockout en cuentas admin. | Matriz por rol/acción completa; cada 403 esperado y ownership testado; SUPER_ADMIN protegido. |
| 3. Errores funcionales críticos | Corregir findings reproducibles de auth, agenda, checkout o pantallas esenciales a partir de pruebas de staging. | Módulos que correspondan al hallazgo confirmado. | No asumir bugs sin reproducción; conservar contratos existentes. | Caso de reproducción, regresión automatizada y aceptación de flujo manual. |
| 4. CRUD y ciclo de vida | Formalizar lifecycle de cada entidad; edición/archivo de historia clínica y estrategia de estudios/adjuntos; retención trazable. | Repositorios/validators/routes clínicos, migraciones nuevas, pantallas correspondientes. | Reglas legales/operativas de historia clínica y storage privado; migraciones fuente incompletas son bloqueo. | Lectura/escritura por permiso y propietario; soft archive/restore cuando proceda; integridad/auditoría. |
| 5. API y backend | Incorporar OpenAPI, errores/respuestas/permisos por endpoint; revisar health y rate limit distribuido. | `backend/src/routes`, validators, README y generación del spec. | No cambiar contratos mobile abruptamente; no divulgar versión/estado sensible. | Comprobación automática spec-route; contrato de cada endpoint; pruebas básicas rate-limit y health. |
| 6. Arquitectura compartida | Asegurar interfaces comunes de mascotas/turnos/productos y reglas comunes en servicios/repositories; consolidar tests de rol. | `mobile/src/components/{clinic,client}`, `backend/src/repositories` y `services`. | Evitar refactor masivo; respetar diferencias por privacidad. | Tests cruzados cliente/vet/groomer/admin sobre fixtures de DB de test. |
| 7. Componentes reutilizables | Reducir duplicación solo donde se confirme lógica/UX equivalente. | Pantallas por rol de agenda, pacientes, perfiles y notificaciones. | Cuidar UX específico de rol y navegación actual. | Pruebas snapshot/interaction y comparación de rutas. |
| 8. Navegación | Probar deep links, rutas protegidas, retorno OAuth, sesión vencida y back stack. | `mobile/src/app/_layout.tsx`, layouts de rol, `GlobalNavigation`, oauth. | OAuth requiere provider/config reales y build nativo. | Matriz por rol + link scheme; sin ciclos/redirecciones, con back correcto en web y Android. |
| 9. Responsive y UX/UI | Prueba manual de teléfono pequeño/grande, tablet y escritorio; foco teclado, modales, lector de pantalla, contraste y decoración. | Mobile componentes, tokens, layouts y formularios. | Requiere dispositivos/browsers de destino; no alterar identidad original. | Checklist por plataforma con capturas y flujo de inputs; huellas no interceptan eventos. |
| 10. Documentación | Alinear versión SDK/RN y guía actual; completar OpenAPI y actualizar estado migraciones desde snapshot fresco. | README raíz, backend/mobile README, `docs/api/`. | Esperar verificación de base y proveedor; no afirmar externo por documento. | CI detecta drift de versión/spec; pasos reproducibles. |
| 11. Pruebas | Añadir integración DB y E2E después de disponer de un ambiente exclusivo de test. | Tests backend integration, mobile tests, flujo de CI. | Debe garantizar nombre de DB `_test`, backups/aislamiento; proveedor fake. | Auth/RBAC/CRUD/checkout probados; no tocar producción. |
| 12. APK y despliegue | Definir package ID final, revisar permisos, credenciales y entornos EAS/Vercel, generar build de prueba. | `mobile/app.json`, `eas.json`, ajustes de proveedor y documentación operación. | Credenciales y publicación externa requieren autorización operacional posterior; nunca generar sobre prod sin confirmación. | EAS build de preview, instalar y validar login/OAuth/push/API; smoke test. |

## Orden de ejecución

Primero consolidar una fuente confiable de esquema y entornos de prueba, luego seguridad/RBAC y lifecycle de datos, y recién después UI y preparación APK. Esto evita que la auditoría conduzca a ejecutar migraciones que no pueden reconciliarse con el historial real.
