## DB-02 - Revalidacion del cambio a Layerbase (2026-10-14)

- `backend/src/config/env.ts` configura TLS para Layerbase/produccion (`DB_SSL_MODE`), rechaza hosts Railway y usa 30 s como timeout predeterminado para permitir el despertar de una base hibernada. La configuracion local ignora `MYSQL_PUBLIC_URL`; se usa exclusivamente `DB_*`.
- La entrada `MYSQL_PUBLIC_URL` del `backend/.env` local no coincidia con host, puerto, usuario, clave ni base de `DB_*`; se retiro de ese archivo ignorado por Git y no se muestra su valor. Si esa URL era la conexion MySQL correcta, volver a copiar sus componentes desde Quick Connect antes de iniciar el backend.
- Quick Connect conecto desde este entorno con verificacion estricta TLS. `SELECT VERSION()` devolvio **MariaDB Server 11.8.9**. La auditoria SQL y las lecturas de esquema confirmaron compatibilidad con el esquema actual: los elementos usados por PetCare (InnoDB, CHECK, columnas generadas e indexadas, transacciones, `FOR UPDATE`, bloqueos nombrados, `ON DUPLICATE KEY UPDATE`, funciones temporales y colacion `utf8mb4_0900_as_ci`) existen en esta rama. El rechazo anterior era una regla conservadora del guard por nombre de proveedor, no una incompatibilidad detectada en las consultas actuales.
- En lectura de metadatos: hay 37 tablas InnoDB; los 28 nombres de tabla y las 143 columnas del inventario versionado estan presentes. Las 34 FK del inventario tambien estan presentes. El esquema de turnos coincide con los campos generados e indices exigidos por `clinic-reconcile.ts`; dos nombres de indices del snapshot `schema-audit.json` son antiguos y fueron sustituidos por indices funcionalmente equivalentes del esquema clinico actual.
- Conteos agregados observados: roles 6, usuarios 2, mascotas 1, turnos 0, productos 0. No se consulto la base anterior de Railway; estos conteos no prueban que sus datos se hayan migrado.
- Se habilito en el guard unicamente MariaDB 11.8.x, conservando el minimo MySQL 8.0.16 y la restriccion a ramas explicitas. Las lecturas de metadatos encontraron que faltaba `users.profile_photo_url`, requerida por la consulta del catalogo clinico. Se aplico la migracion existente `db:migrate:profile-photo`, que agrega solamente `VARCHAR(2048) NULL` y no modifica filas existentes. No se ejecutaron migraciones destructivas, seeds ni escrituras de datos. Tras esto, funcionaron lecturas seguras mediante repositorios de autenticacion, mascotas, catalogo y turnos; no se consultaron datos de Railway.
- `mobile/vercel.json` configura solo el frontend. No se accedio al panel de Vercel y no se modificaron variables remotas. La variable mobile de produccion debe apuntar al backend real (`EXPO_PUBLIC_API_URL=https://<api-confirmada>/api`); las credenciales DB solo van en el entorno backend.
- Verificacion: `npm test` (3/3), `npm run typecheck`, `npm run lint` y `npm run build` pasaron. `npm run db:check` paso contra Layerbase. Lecturas reales: auth lookup (email sintetico sin coincidencia), mascotas (0 filas para owner 0), catalogo de especies/razas, turnos (0 para owner 0) y catalogo clinico (2 tipos, 0 servicios). `DATABASE()` coincide con DB_NAME; `SHOW SESSION STATUS` confirmo TLS cifrado. La base anterior de Railway no se inspecciono, por lo que no se afirma que esos datos existan en Layerbase.
- Accion previa a Cloudinary: confirmar en el panel Layerbase que los valores DB_* locales correspondan al endpoint y esquema que se publicaran; configurar esos mismos valores y TLS en el entorno del backend publicado. No hacen falta cambios de motor ni migraciones para resolver la incompatibilidad de version identificada.
